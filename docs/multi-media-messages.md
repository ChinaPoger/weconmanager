# 一条消息里的多个媒体

## 0. 结论先行

企微的一条消息**本来就可能带多张图**。我们的模型假设「一条消息 = 至多一张图」,
这个假设从一开始就是错的,只是被「取不到图」掩盖着 —— TCP 通道修好之前,这些图
根本走不到需要排版的那一步。

mars 侧**在 png/jpeg/gif/webp/bmp 范围内不需要改动**:`Content` 是纯文本,前端把
文本里**每一个被识别为图片的** URL 都渲染成图并竖排。HEIC 和认不出格式的 `.bin`
是例外,见 §3。

但有一条比排版重要得多的约束:**`Content` 参与 mars 的去重 checksum**,所以它必须
在一条消息的所有投递尝试之间保持一致。现有单图代码并不满足这一点,多媒体只会放大
它。**先做 outbox,再做多图**(§2、§8)。

---

## 1. 第一性:领域对象是一棵树,不是一个标量

企微消息正文是嵌套 protobuf。媒体票据(`fileid`/`size`/`aeskey`/`md5`)会出现在
树的**任意深度**,实测到的路径:

| 路径 | 含义 |
|---|---|
| 顶层 | 普通图片消息 |
| `pb1→pb103` | 图文混排消息里的图 |
| `pb1→pb17→pb1002→pb1→pb103` | **引用回复**里被引那条的图 |
| `pb1→pb107→pb1→pb103` | **合并转发的聊天记录**里的图,一条记录 N 张 |

现有代码只看顶层(`image_ticket` 读 `fields[1][0]`),所以整棵树的其余部分全漏了。

实测(最近 400 条 `ct=4`,其中 121 条处于 pending):

| 去重后真图张数 | 消息数 |
|---|---|
| 0 | 24 |
| 1 | 46 |
| 2 | 34 |
| 3 | 6 |
| 4 | 2 |
| 5 | 4 |
| 6 | 3 |
| 8 | 1 |
| 11 | 1 |

**97 条有图,其中 51 条是 2 张以上**,共 201 张真图。

所以正确的抽象是 `消息 → 媒体列表`,而不是 `消息 → 那张图`。

## 2. 第一性:`Content` 是去重键,所以它必须是消息的确定性函数

mars 侧(`models/qq.go`):

```go
rawStr := fmt.Sprintf("%s%s%s%s",
    message.GroupNumber, message.SenderNumber,
    message.SendTime.Format("2006-01-02 15:04:05"), message.Content)
message.Checksum = fmt.Sprintf("%x", md5.Sum([]byte(rawStr)))
```

**这一条决定了整个设计。** 正文里少一个 URL,checksum 就变,mars 眼里就是**另一条
消息**。于是:

> 同一条消息**先推 3 张图、后来补推 5 张图**,不是「更新」,是**两条重复记录**。

mars 侧的写入是按 checksum 的 upsert(`models/qq.go`):

```go
database.Where(Message{Checksum: msg.Checksum}).Assign(*msg).FirstOrCreate(msg)
```

`Checksum` 上有唯一索引。所以**同 checksum 会更新同一行,不同 checksum 会插入新行**。
mars 没有用 LID 或任何稳定的源消息 ID 去找原行,因此「补一张图再推一次」必然是新行。

### 正确的约束表述

不是「一条消息只推一次」,而是:

> **同一条源消息的 Content,必须在它的所有投递尝试之间保持一致。**

这个区别是实质性的,因为同步器本来就会重试:推送成功但响应丢失、进程在
`push_one` 成功和状态落盘之间崩溃、显式 backfill、tombstone 续推 —— 这些路径下
水位没推进,下一轮会重新生成 Content。

### 当前方案在这一点上是**不达标**的

§5.4 写着「单张失败保留 `[图片]`」。于是:

1. 第一轮某张图没取到 → Content 里是 `[图片]`,推给 mars;
2. mars 写入成功,但响应在网络里丢了 → 我们认为失败,水位不动;
3. 第二轮那张图取到了 → Content 变成 URL → checksum 变 → **mars 多一行**。

也就是说 Content 是「消息 + 当时的缓存/网络状态」的函数,而不是消息的函数。
**这不是本设计引入的问题,现有单图代码就有**(`message_body` 每次重新调
`media.resolve()`),只是媒体从 1 个变成 N 个之后,漂移的概率成倍上升。

而且 hook 整体并不幂等:`qq/qq.go` 在 Upsert 之后还会无条件触发告警、转发、
Slack、活跃时间更新 —— 同 checksum 重投虽然只有一行,副作用仍会重复。

### 必须选一个

1. **本地 outbox(推荐)**:第一次决定推某条消息时,把**最终 Content** 落盘;
   所有重试复用这份字符串,不再重新解析媒体。Content 因此真正只由「首次决定」
   确定,重试完全一致。
2. 持久化每个媒体项的终局决定(「用这个 URL」/「永久占位符」),等价但更细。
3. 改 mars,加一个稳定的源消息 ID 并按它 upsert —— 成本最高,但根治。
4. 明确接受这个重复风险并写进文档 —— 不能像本文最初那样,声称确定性设计已经
   消除了它。

本设计选 **1**。它同时把「§5.4 的部分失败」和「§7 的部署边界」两个问题一起解决。

`_object_key` 的注释里已经写过同一条原则(「key 必须是确定的,否则同一条消息每重推
一次就多出一个对象」),outbox 是它在正文层的对应物。

## 3. 第一性:mars 前端已经支持多图

`website/src/modules/qq/components/QqMessageContent.vue`:

```js
const re = new RegExp(pattern, 'gi')
while ((m = re.exec(text)) !== null) {        // 全量匹配,不是第一个
  if (m.index > last) out.push({ type: 'text', value: text.slice(last, m.index) })
  out.push({ type: 'image', value: m[0] })
  last = m.index + m[0].length
}
```

```css
.qq-msg-image { display: block; }             /* 每张独占一行 */
```

所以:**多个 URL → 多张图,竖排。** hook 模型、DB 列、前端组件都不用动。

一个**必须注意的坑**:模式按类型切换 ——

```js
const pattern = typeInfo.value.type === '图片' ? HTTP_URL : IMAGE_URL
```

`messageType === '图片'` 时用的是 `HTTP_URL`,即**正文里任何 http 链接都会被当成图**
去 `<img>`。合并转发的聊天记录里往往夹着普通链接(实测有 Grafana、kubeadmin 等),
如果我们把这类消息的 `messageType` 报成「图片」,那些链接会渲染成碎图。

### 扩展名:这里有个真实的缺口

`IMAGE_URL` 的白名单只有 **png / jpe?g / gif / webp / bmp**。而我们的 `ext` 有两条
路会落在白名单之外:

- `media.py:428` 的 CDN content-type 映射里有 `"image/heic": ".heic"`;
  `_MEDIA_NAME`(`media.py:66`)也把 `heic` 当图片文件名 —— iPhone 发的原图就是 HEIC。
- 认不出魔数时兜底成 `.bin`:`media_tcp.py:489`,以及 `media.py:406` 的
  `os.path.splitext(path)[1].lower() or ".bin"`。

**`.heic` 和 `.bin` 在 mars 前端一律不渲染**(非「图片」类型时连 `<img>` 都不会生成)。

实测:当前样本里 65 张成功下载的图全是 `.png`/`.jpg`,嵌套载荷的文件名也只有
51 个 `.png` + 2 个 `.jpg` + 10 个无名。所以这是**低频但结构性可达**的缺口,
不是理论问题。

处置(三选一,本设计选第一条):

1. **上传前统一转码**成 png/jpeg,或至少保证后缀与实际字节一致且在白名单内;
2. 扩 mars 的 `IMAGE_URL` 白名单(要改 mars,和「零改动」矛盾);
3. 接受 HEIC/未知格式不显示,并记日志。

所以 §0 那句「mars 侧不需要任何改动」要收窄成:**在 png/jpeg/gif/webp/bmp 范围内
不需要改动**。这一点是本文最初写错、经复核修正的。

## 4. 判据:图 / 附件 / 装饰,三类要分开

同一个「票据形状」`{1,4,8,10}` 会同时匹配到**文件**,实测:

| `[2]` 文件名 | size | `[8]` aeskey |
|---|---|---|
| `tstest.zip` | 45.75 MB | **空** |
| `osins-ls-app-qiniu.zip` | 37.00 MB | **空** |
| `企业微信截图_a165….png` | 1.18 MB | 32 位 hex + 尺寸 1292×1930 |
| `AGENTS.md` | 3103 B | **空** |

判据:

- **图**:字段 8 是 **32 字节 ASCII hex**,hex 解码后得到 **16 字节** AES key;
  `md5` 是 32 位合法 hex;`size` 是正整数;`fileid` 非空。
  (`media_tcp.py:129-134` 就是这么校验的,`decrypt_filedata` 直接拿它做
  AES-128-ECB。原始字段长度和解码后长度别混为一谈 —— 32 vs 16。)
- **附件**:同样的字段号,但字段 8 为**空** → 构造不出 `ImageTicket`,现有下载
  解密路径处理不了。`[2]` 是文件名,可作为文本展示。
- **装饰**:整棵树里**没有**任何票据,而 `extract_filename` 抠到了
  `icon.png` / `avatar_24.*.png` / 卡片缩略图。这类根本不是本条消息的附件
  (链接卡片已在 PR #12 处理,这里是同一类的推广)。

⚠️ 「空 aeskey ⇒ 一定是附件」是**当前样本下的归纳**,不是协议保证。代码只能证明
「空 key 走不了这条图片通道」。所以实现上应该保留一个 `unknown` 分类兜底,不要
断言未来所有文件类型都必然空 key,也不要断言不存在另一套文件下载协议。

顺带修正一个早先的担心:按正确判据统计,真图 **最大 4.61 MB、中位 0.14 MB、
没有一张超过 `MAX_DOWNLOAD_BYTES`(32MB)**。之前看到的 45MB 是 zip,不是图。

## 5. 设计

### 5.1 抽取:`collect`

```python
@dataclass(frozen=True)
class MediaItem:
    md5: str
    size: int
    filename: str                  # 嵌套载荷的 pb2
    kind: Literal["image", "file"]
    ticket: ImageTicket | None     # kind == "image" 时非空

def collect(content) -> list[MediaItem]:
    """正文 → 这条消息携带的全部媒体,**文档序**,按 md5 去重。"""
```

**顺序是「规范序」,不是「文档序」。** 这点必须说清楚:按字段号升序遍历是**确定的**
(同样的字节必然得到同样的顺序),但没有证据表明字段号顺序 == 用户在企微里看到的
聊天记录顺序。本设计只承诺前者。要承诺后者,得先拿实测把 `pb107` 里 repeated 子消息
的 wire order 和界面顺序对上。

排序规则要完整定义,否则「保留首次出现」没有意义:

1. 字段之间:**字段号升序**;
2. 同一字段号的多个 occurrence:**保持原始 wire order**(不能进无序容器);
3. 深度优先。

**递归条件要收紧。** 不能因为一段 bytes「碰巧能被 protobuf 扫完」就当它是嵌套
message —— 字符串、fileid、md5 这些 opaque 载荷都可能偶然解析出 `{1,4,8,10}` 形状。
实现上:

- 只递归**能被完整消费**、且字段号/wire type 都合理的 length-delimited 内容;
- 设深度上限、节点数上限、总字节上限;
- 优先按实测到的容器字段(`103`/`107`/`1002`/`17`)做半白名单,而不是无约束递归。

⚠️ **深度上限是输出规范的一部分**,不是可以随手调的防御参数。把 6 改成 8,同一条
历史消息的媒体列表就可能变化 → Content 变 → checksum 漂移(§2)。改它等同于改协议。

**去重键是 `(kind, md5)`,并且 image 优先于 file。** 只按 md5 去重不够:先遇到一个
空 key 的 file、后面才遇到同 md5 的可下载 image 时,保留 file 会把能取的图丢掉。
相同 md5 不同文件名时保留首次出现的文件名。

`locate()` / `pending()` / `resolve()` 全部改成基于 `collect` 的列表版本;
单图是「列表长度为 1」的特例,不再有两套逻辑。

### 5.2 就绪判定:从「那张到了吗」到「这一组齐了吗」

```
pending(msg) = 窗口未过期 and 存在 kind=="image" 的项还没有本地文件
```

`_ready_count` 语义不变:本群卡住,直到齐了或窗口到期。变化只在于「齐」的定义
从一张变成一组。

### 5.3 排版

```
[图片] → url1                      # 原有占位符替换,保持不变
url2
url3
...
```

每个 URL 独占一行。理由:前端 `.qq-msg-image{display:block}` 本来就竖排,
而换行让**没被渲染成图时**(URL 挂了、前端旧版本)退化成一行一个链接,仍然可读。

附件不下载,渲染成文本行:`[文件] tstest.zip`。

`messageType` **保持现状**,不要为了多图把合并转发报成「图片」—— §3 那个
`HTTP_URL` 分支会把记录里的普通链接变成碎图。我们的 URL 自带扩展名,
走 `IMAGE_URL` 就能渲染。

### 5.4 预算与上限

一条 11 张图的消息 = 11 次 TCP + 11 次上传,而它**卡着本群的同步**。

- `mars_image_max_per_message`(默认 9):超出部分不取,正文末尾追加
  `(另有 N 张未展示)`。**这是确定性的**(取的是文档序前 N 张),不违反 §2。
- 整条消息共享一个时间预算,而不是每张图各等一个 `mars_image_client_wait`。
- 单张失败不影响其余:失败的那张保留 `[图片]` 占位符文本。

### 5.5 不做的事

- **不做「先推后补」**。§2 已经证明那是制造重复,不是修复。
- **不改 mars**。hook 模型、DB、前端都够用。
- **不下载附件**。没有 aeskey,拿不到明文;把文件名写进正文即可。

## 6. 风险

| 风险 | 处置 |
|---|---|
| **重试间 Content 漂移 → mars 多一行** | **第 0 期 outbox**(§2)。这是最高优先级,且现有单图代码已经有这个洞 |
| Phase 1 改变已推消息的 Content | 部署切换水位 + 禁止跨点回放(§8) |
| HEIC / `.bin` 在 mars 不渲染 | 上传前转码或跳过(§3);当前样本未命中,但结构上可达 |
| 11 张图卡住一个群 | §5.4 的上限 + 整条预算 |
| 合并转发里的链接被渲染成碎图 | 不把这类消息报成 `messageType='图片'`(§5.3) |
| 递归把 opaque 字节误认成嵌套 message | 收紧递归条件 + 半白名单(§5.1) |
| 调整深度上限导致历史 Content 变化 | 深度上限视作协议的一部分,改动等同于改协议(§5.1) |
| 同一张图在正文和引用里各出现一次 | 按 `(kind, md5)` 去重(§5.1) |

> 本节连同 §2/§3/§5.1/§8 的多处结论,来自一次外部复核。最初版本里
> 「一条消息只推一次就没有重复风险」和「对象 key 总是图片扩展名」两条是**错的**,
> 已按代码证据改正。

## 7. 上游门槛:光改 media 是够不着的

`collect` 再强,拿不到正文也没用。`messages.py:676`:

```python
"raw": r["content"] if ctype in IMAGE_TYPES or rich_image else None,
"quote_raw": quote_payload if quote_text == IMAGE_PLACEHOLDER else None,
```

- `raw` 只在 `ctype ∈ {4,14,29}` 或 `rich_image` 时保留;
- `quote_raw` 更严 —— 得先被**旧的扩展名摘要**认成图片才会带上。

于是「任意嵌套深度」这个目标,在顶层类型不在集合里、或引用摘要没认出图时,
根本到不了 `collect`。**这两个门必须和 `collect` 同期改**,否则设计宣称覆盖的
合并转发场景仍然不可达。

同时要定义**媒体与正文段的归属**:现在 `raw` → `text`、`quote_raw` → `quote_text`
是两段分开解析的。改成一条消息一个媒体列表后,要说清楚:

- 媒体列表是否跨 `raw` 和 `quote_raw` 合并(会影响去重);
- URL 放正文还是放 `> 引用: ` 后面;
- 跨正文/引用去重时,会不会把引用里那张图删掉。

本设计的取向:**两段各自 `collect`、各自去重**,不跨段合并 —— 保住「正文和引用
从头到尾没合并过」这条既有不变量(`message_body` 的 docstring 说明了为什么)。

## 8. 分期

| 期 | 内容 | 备注 |
|---|---|---|
| **0** | **outbox**:落盘首次决定的 Content,重试复用 | §2 的前提。**必须先做**,否则后面每一期都在放大重复风险 |
| **1** | `collect` + `messages.py` 两个门 + 附件文本化 + 仍只用第一张 | 46 条受益 |
| **2** | 多图排版 + 上限 + 预算 | 51 条受益 |
| **3** | 格式兜底(HEIC/`.bin` 转码或跳过) | §3 的缺口 |

「装饰过滤」不单独成期:按 §5.2 的新定义,没有票据就不会产生 image 项,也就
不会 pending —— 它被第 1 期自然吸收了。(前一版把它列成独立一期是重复计算。)

### Phase 1 自己就会改 Content

这是最容易被忽略的一点。旧逻辑对某条消息推的是 `[图片]`,Phase 1 找到了深层票据、
推成 URL —— **同一条消息的 Content 变了**。正常路径下无所谓(水位已经推进,不会回看),
但一旦发生 §2 那些重放场景,就会在 mars 里留下第二行。

而且即使新旧都只取一张,「哪一张」也可能不同:旧 `locate()` 是全文搜 md5/文件名,
新 `collect()` 是规范序取第一个,含多个嵌套票据时两者没有理由选中同一个。

所以 Phase 1 **不是**向后兼容的纯增强,而是一次 Content 生成规则变更。部署要求:

- 上线时**记录每群的切换水位**;
- 切换点之前的消息即使被重放,也不得用新规则重算 Content(或干脆禁止自动回放);
- backfill 明确不许跨过该切换点;
- 有了第 0 期的 outbox,正在重试中的消息用的是已落盘的旧 Content,这条边界才真正守得住。
